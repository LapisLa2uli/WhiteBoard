WhiteBoard release and commit tips
==================================

Read this file before every commit that is part of a release, and before
tagging or publishing on GitHub. These rules stay here so they are not lost
when chat history is summarized.

Changelogs
----------
- Write for a person who just downloaded the app, not for developers.
- Say what they will notice: new buttons, new screens, "the app opens now",
  "sign-in no longer fails", and similar.
- Do not use packaging jargon (PyInstaller, Playwright, Flet, Chromium
  revisions, wheels, hooks, CI job names) unless a sentence is impossible
  without a short plain-language gloss.
- Every version in CHANGELOG.md must have these three headings, in this order:

    ### Added features
    ### Bugfixes
    ### Other changes

- Put those same three headings on the GitHub release under the version title.
  GitHub release notes are generated from CHANGELOG.md. If a heading has
  nothing to say, write a single line such as "- None in this release."
- Packaging fails if the current app version has no CHANGELOG section or is
  missing those headings.

Installers on every GitHub release
----------------------------------
- Every 0.4.0 release must include both supported launchers:
    1. Windows setup (.exe)
    2. macOS Apple Silicon (.dmg)
  Intel macOS is outside the 0.4.0 release scope.
- Do not publish if either is missing. Do not let a Windows-only
  build go out as a full release.
- After a tag is pushed, confirm both files and SHA-256 checksums
  are listed on the release page before telling anyone it is done.

Broken releases
---------------
- If a shipped version has a fatal bug (for example it quits as soon as you
  open it), mark that GitHub release as known not to work:
    Title: "WhiteBoard x.y.z (known not to work)"
    First line of the notes: a plain warning, plus which version to use instead.
- 0.1.0, 0.1.1, and 0.1.2 are in that category (they do not start). Do not
  un-mark them.

Re-tagging
----------
- Only move an existing version tag (for example re-release 0.1.3) when the
  user asked to re-release that same version.
- Do not force-push the master branch.

How to cut a release
--------------------
The app you develop and run is the repository root (`python run.py`).
The previous Flet app, its installer, and its tests are in archive/original/.

1. Set APP_VERSION in version.py for the current app. Leave archive/original alone.
2. Add CHANGELOG.md notes using the three headings above.
3. Commit each improvement separately. Run python tools/test.py and native packaged smoke tests.
4. Follow packaging/README.md to build Windows x64 and Apple silicon from the same clean revision.
5. Verify signatures, notarization, install/update/uninstall and clean-machine launch before publishing.
6. Push/tag/publish only when requested. Confirm both installers, checksums and readable notes.
